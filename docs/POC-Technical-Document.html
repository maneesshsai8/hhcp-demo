HHCP "Octane" — Business Operating System

Proof-of-Concept Technical Document

A multi-tenant EOS / Traction-style "business operating system" (a purpose-built ninety.io replacement) for a private-equity fund. This document explains, module by module, what the system does, the technology and database behind it, how the data is related, and how it is deployed.

1. Executive summary

The platform lets a fund and its portfolio companies run the EOS toolkit — Vision, Scorecards, Rocks, To-Dos, Issues, Meetings, Accountability, Announcements — inside one system, while keeping every company's data strictly isolated. The hardest technical risk (secure multi-tenant data isolation across a Fund → Portfolio Company → Add-on hierarchy) was proven first, then the feature modules were built on top of it.

The one big idea: authorization is enforced by the database on every single request (PostgreSQL Row-Level Security), not by application code. This means a bug in the app cannot leak another company's data, and revoking access takes effect on the very next request.

2. Architecture at a glance

The system has four cooperating layers plus a realtime channel:

LayerTechnologyResponsibility
Client (browser)Next.js 14 (React 18)The UI. Holds no auth token in JavaScript; the login token lives in an httpOnly cookie.
Request planeFastAPI (Python, async) + asyncpgProves who you are, then runs plain SQL. It never decides what you can see.
Data planePostgreSQL 16 (inside Supabase)Decides what you can see via Row-Level Security. Single point of enforcement.
Durable planeBackground worker (separate process)Does slow / after-the-fact work: meeting summaries, emails, calendar sync, realtime publish — reliably, even if a request crashes.
RealtimeSupabase Realtime (Broadcast + Presence)Live meeting sync — who is present, and "refresh this now" signals.

Request flow (simple):

  1. Browser sends a request with its httpOnly cookie.
  2. FastAPI verifies the token and identifies the user (only identity, nothing more).
  3. FastAPI opens one database transaction and tells Postgres "the current user is X".
  4. The app runs ordinary SQL with no "WHERE tenant = ..." filter.
  5. Postgres automatically filters every row to only what user X may see (RLS).
  6. The result returns to the browser. Slow follow-up work is handed to the durable worker.

4. Multi-tenancy — the tenant hierarchy

Every piece of data belongs to a "tenant" (an organization). Tenants form a three-level tree:

  • Fund (e.g. Hidden Harbor) — the top.
  • Portfolio Company (PortCo) — each company the fund owns.
  • Add-on — a bolt-on acquisition under a PortCo.

Access cascades down. If you are granted a PortCo, you automatically get its Add-ons. A Fund Admin sees the whole portfolio (read/rollup). A PortCo manager sees only their company and cannot even discover the others exist.

This tree is stored in one table (organizations) where each row points to its parent (parent_tenant_id). The recursive "who can this user see" logic lives in a database function, user_accessible_tenants().

5. Platform — Authentication & Authorization

This is the foundation every module depends on.

Authentication (who are you?)

  • Users sign in through Supabase Auth (email/password, Google, or Microsoft). Supabase issues a signed token.
  • The browser hands that token to the backend, which stores it in an httpOnly cookie — so it is never readable by JavaScript (protects against token theft).
  • On each request the backend verifies the token and maps it to an internal user record (users.supabase_uid → users.id). Token refresh is handled server-side.

Authorization (what can you see / do?)

Two layers, both in the database:

  1. Tenant isolation (Row-Level Security): every tenant table has a policy: a row is visible only if its tenant_id is in user_accessible_tenants(current_user). Fund admins get all tenants; everyone else gets their granted tenants plus all descendants (the cascade). No session set = zero rows (safe default-deny).
  2. Within-tenant scoping: on Scorecards/Rocks/To-Dos/Issues a second rule limits what a junior role sees inside a tenant — a "team member" sees only records they own; a "manager" also sees their direct reports' records; senior roles see everything in the tenant.

Role matrix (RBAC): fund_admin / lead_partner / deal_qb / portco_management / manager can view + create + edit + delete; ops_qb / addon_management / team_member can view + create + edit; read-only roles can only view. Provisioning new companies is fund-admin only.

Why this is strong: because the check is in Postgres, even a mistake in the API cannot return another company's data. Revoking a grant takes effect on the next request — no waiting for a token to expire.

5.1 How RLS, tenant scoping & RBAC interlink — a worked example

These are three separate checks that stack. Every request passes through all three, in order — each answers a different question:

CheckQuestion it answersWhere it lives
1. RLS (tenant isolation)"Which companies' rows may you touch at all?"A Postgres policy on every table: a row is visible only if its tenant_id is in user_accessible_tenants(you).
2. Tenant scoping (the cascade)"Does a grant on a parent company include its children?"Inside user_accessible_tenants(): a grant on a PortCo expands to all its Add-ons (recursive walk of the org tree).
3. RBAC"Which records inside those companies, and what may you do to them?"(a) A second RLS layer scopes records by ownership for junior roles; (b) the API's role matrix allows/denies the action (view / create / edit / delete).

Cast (from the demo data): Priya is an ops_qb granted Restaurant A + Restaurant C. Restaurant A has an Add-on, Food Truck. Tom is a team_member in Restaurant C who reports to Mia (a manager).

Example — Priya opens the Rocks page:

  1. RLS runs user_accessible_tenants(Priya) → {Restaurant A, Restaurant C, Food Truck}. Food Truck is included automatically because it is an Add-on of Restaurant A (that is tenant scoping / the cascade). So Priya sees Rocks from exactly those three companies — never Restaurant B, never the Fund.
  2. Within-tenant scoping: because ops_qb is a senior role, she sees all Rocks inside those companies (a team_member would see only their own).
  3. RBAC action matrix: ops_qb may view / create / edit but not delete — so the UI shows no Delete button, and a delete call would be refused.

The same three checks can each block a request — at a different layer:

  • Priya tries to edit a Rock in Restaurant B (even guessing its ID): RLS blocks it — Restaurant B isn't in her accessible set, so the UPDATE matches zero rows and returns 404. The database refuses to release the row no matter what the API asks — this is why an app bug cannot leak data.
  • Tom tries to delete a Rock he owns in Restaurant C: RLS passes (Restaurant C is his), within-tenant passes (he owns it), but the RBAC action check blocks it — a team_member has no delete permission → 403.
  • Tom tries to open a co-worker's Rock he doesn't own: RLS passes (same company), but within-tenant scoping hides it (team members see only their own records; his manager Mia would see it as his direct report).

In one line: identity → RLS picks the companies → within-tenant scoping picks the records → the RBAC action matrix decides what you may do. A request only succeeds if it clears all three — and the first two are enforced by the database itself, so they cannot be bypassed by the application.

6. Modules

6.1 Scorecard

Purpose: track weekly/monthly KPIs ("measurables") with Red / Amber / Green status against a goal.

How it works: each measurable has a goal, a direction (higher/lower is better), and green/red thresholds. Each period you enter a value; the status is computed. Three consecutive RED weeks automatically raise an Issue (once). Measurables can be grouped into named sections and laddered to a VCB.

Tech & DB: append-style history table; entering a value is an upsert keyed to the period. Excel/PDF export shades cells by status.

TableStoresRelated to
kpisThe measurable: title, goal, thresholds, direction, frequency, unit, ownertenant_id → organizations, owner_id → users, group_id → kpi_groups, vcb_id → vcbs
kpi_scoresOne value per period (recorded_at + actual_value)kpi_id → kpis, tenant_id → organizations
kpi_groupsNamed sections on the scorecard (e.g. "Sales KPIs")tenant_id → organizations

Flow: Create measurable → enter weekly value → status auto-computed → 3 reds in a row → Issue auto-created → export to Excel/PDF.

6.2 Dashboard (Portfolio rollup / Data federation)

Purpose: the fund's cross-company view — totals of Rocks, Issues, To-Dos, KPIs, VCBs rolled up the Fund → PortCo → Add-on tree.

How it works: a "query-time fan-out" — the backend runs a handful of GROUP BY queries (still under RLS, so scoped to what the caller can see) and rolls the numbers up the hierarchy in code. It reports how many tenants were scanned and how long it took, so scaling is observable. No extra tables — it reads the live module data.

Tech & DB: read-only aggregation across existing tables; two future scaling options are documented (event-driven from the audit log, or a nightly materialized rollup table).

Flow: open Dashboard → backend fans out GROUP BY per tenant → rolls up the tree → shows per-company + portfolio totals (admins see all; a PortCo user sees only their subtree).

6.3 Rocks (quarterly priorities)

Purpose: 90-day priorities, each with an owner and a status (On-track / Off-track / Complete).

How it works: Rocks can have multiple assignees (the first is the primary owner) and can "ladder up" to a VCB workstream. Views: List (grouped by owner), Planning Board (by status), Blueprints (the VCB view), Archive (completed).

TableStoresRelated to

Flow: Create Rock (owner, due date, optional VCB workstream) → update status as the quarter progresses → in a meeting's "Rock Review" the status can be changed live.

6.4 VCBs (Value-Creation Blueprints)

Purpose: the PE-specific layer — an investment thesis broken into workstreams, each containing Rocks, with a live progress rollup.

How it works: VCB → Workstreams → Rocks. Progress % = completed Rocks / total Rocks. VCBs are edited by leadership; Rocks stay at manager level. The VCB view is folded into the Rocks module as a "Blueprints" tab, and you can add a Rock straight into a workstream.

How it works: Team vs Private tabs (a private to-do is only visible to its owner, enforced in the database), priority, weekly "carry-forward" logging of overdue items, completion notes, and completion-rate stats. To-Dos can be created from an Issue or a Scorecard.

6.6 Issues (IDS list)

Purpose: the Identify–Discuss–Solve list of things to work through.

How it works: Short-Term / Long-Term / Resolved tabs, drag-to-rank priority, owner, category, priority, link to a VCB, resolve-with-note. Resolving is a checkbox; an "…" menu offers Create-To-Do / Resolve / Delete.

6.7 Meetings (Level-10 runner)

Purpose: run a structured, timed EOS meeting live and keep a history.

How it works: a timed agenda (Segue, Scorecard, Rock Review, VCB Review, Headlines, To-Do List, IDS, Conclude). Each section shows the tenant's real Scorecard/Rocks/To-Dos/Issues data and lets you act on it live (change a Rock's status, tick a To-Do, raise an Issue). Multi-user presence + live sync via Supabase Realtime. On finish it saves attendance, a per-user rating, and an auto-generated summary.

Tech highlight — reliability: completing a meeting writes the change and an "event" in the same database transaction (a transactional outbox). A separate background worker then generates the summary, sends notifications, and publishes the realtime update — so nothing is lost even if a request crashes. Meeting state uses optimistic concurrency (a version number), returning a 409 if two people change it at once; the client simply resyncs.

Posting fans out in-app + email notifications (email really sends), and leadership sees an ack tracker (who read / acknowledged). The fan-out runs in the background worker.

7. Deployment plan

Current (POC / local)

  • PostgreSQL + Auth + Realtime run locally via the Supabase CLI + Docker.
  • Backend: Uvicorn on port 8000. A second process runs the background worker.
  • Frontend: Next.js dev server on port 3002.

Target (production)

Important — Vercel is for the frontend only. Vercel hosts the Next.js app, but it does not run our Python/FastAPI backend. Vercel's functions are short-lived Node/Edge runtimes; our backend is a long-running async Python service that keeps a database connection pool open and also runs a persistent background worker. So the backend needs its own place to run — its own "API compute".

Performance & scale

  • Horizontal scaling: the API is stateless (the session lives in the cookie, not in server memory), so you scale by adding instances behind a load balancer — no sticky sessions needed.
  • Connection pooling: each API instance keeps an asyncpg pool; put Supabase's connection pooler (Supavisor / PgBouncer) in front so many instances don't exhaust Postgres connections.
  • RLS is cheap: user_accessible_tenants() is a STABLE function (evaluated once per statement, not per row), tenant_id is indexed on every table, and the cascade walks a tiny org tree — so the security layer adds negligible latency.
  • Time-series volume: the high-growth tables (kpi_scores, notification_deliveries) are partitioned (pg_partman + BRIN indexes), so they stay fast as history accumulates.
  • Slow work is decoupled: summaries, emails and calendar sync run in the background worker via the outbox, so request latency stays low; scale throughput by adding more workers (SKIP LOCKED keeps them from double-processing).
  • Realtime is offloaded: live meeting sync uses managed Supabase Realtime — there is no socket server for us to scale.
  • Frontend speed: Vercel's CDN + Next.js caching give fast global loads.
  • One thing to change for multi-instance: the demo's rate limiter is in-process (per instance). In production, move it to Redis or the API gateway so the limit is shared across all instances.

Database migrations & safety gates

  • migrate.py — a forward-only migration runner over numbered SQL files, with checksum drift detection (you cannot silently edit applied history) and a guard on non-idempotent one-shot migrations.
  • check_isolation.py — a CI gate that inspects the live schema and fails the build if any table is not tenant-isolated (tenant_id + RLS + policy), unless it is on a small, reviewed global allowlist. This permanently closes the "developer forgot to enable RLS on a new table" gap.
  • Recommended CI: on a fresh database, run migrate.py apply then check_isolation.py; a non-zero exit blocks merge.

Security & isolation guarantees (summary)

  • Every tenant table is protected by Row-Level Security — isolation is enforced by the database, not trusted to app code.
  • The login token is never exposed to JavaScript (httpOnly cookie).
  • Realtime uses private, tenant-scoped channels — a user from another company cannot subscribe to a meeting they can't access.
  • The app's database role is not a superuser and cannot bypass RLS.
  • A CI conformance gate mechanically enforces that every new table stays isolated.

8. How it all connects (one-paragraph recap)

Next.js talks to FastAPI over cookies. FastAPI proves identity, then runs plain SQL inside one transaction that tells Postgres who the user is; Postgres Row-Level Security returns only that user's tenants (cascaded down the Fund → PortCo → Add-on tree). Each feature module (Scorecard, Rocks, VCBs, To-Dos, Issues, Meetings, Users, Announcements, Vision, Dashboard) is a set of tenant-scoped tables plus endpoints; anything slow or "must-not-be-lost" (meeting summaries, emails, realtime) is handed to a durable background worker via a transactional outbox. The result is a secure, multi-tenant EOS platform that is simple to reason about: the database is the single source of truth for both data and permissions.
